# Task completion ("Concluir") stays inside the gsh-events sandbox

`ADR-0001` and `ADR-0002` cover the two core patches that make hard gates possible: blocking Opportunity creation/stage-advance (`opportunityStageAdvanceGateHandler`) and blocking individual field edits on the cadeia de formalização (`recordFieldPersistGateHandler` in `usePersistField.ts`). Once the drip-task pattern was reverted and all four formalization tasks started being created together (see `CONTEXT.md` — Concluir), the remaining gap was the other direction: a task-first way to advance the chain, so the seller doesn't have to leave the "Status agora" widget and go edit the Opportunity/ServiceOrder/Proposal record just to fill the field a task is asking for.

**Decisão:** implementar "Concluir" (mini-formulário por tarefa, em `status-now.front-component.tsx`) inteiramente dentro do pacote `gsh-events`, como front-component sandboxado. Ao confirmar, ele chama as mutations GraphQL necessárias direto pelo client SDK do app (`CoreApiClient.mutation` — ver `complete-stage-transition-task.service.ts`): atualiza o(s) campo(s) correspondente(s) (ex.: `sentAt` da proposta, `eventClosedAmount`/`eventAcceptanceEvidence` da Opportunity) e marca a Task como `DONE`, na mesma sequência que um usuário faria manualmente. Essas mutations passam pelos mesmos hooks de core (`usePersistField`/`useUpdateOneRecord`) e portanto pelo mesmo `recordFieldPersistGateHandler` da ADR-0002 — "Concluir" não contorna o gate de campo, só empacota os passos num clique.

**Alternativa rejeitada:** replicar o padrão de `useRegisterOpportunityStageAdvanceGateHandler`/`openModal` da ADR-0001 para o checkbox nativo de tarefas (`TaskRow.tsx` → `useCompleteTask.ts`) — ou seja, um terceiro patch de core que intercepta `updateOneRecord` no objeto Task e abre o mini-formulário de lá. Rejeitada por dois motivos: (1) exigiria duplicar, num segundo runtime de core (`twenty-front`), as mesmas regras de "qual tarefa corresponde a qual campo/gate" que já vivem em `gsh-events` (`complete-stage-transition-task.service.ts`, `OpportunityProductionGateModal.tsx`) — os dois lados não compartilham código diretamente (`gsh-events` roda como projeto Yarn standalone fora do workspace raiz, ver nota em `gsh-task-titles.ts` sobre a decisão da issue #58); (2) o patch de core existente (`recordFieldPersistGateHandler`) já basta pra impedir que qualquer caminho — incluindo esse checkbox nativo — persista um campo fora de ordem. Um terceiro patch só pra abrir um modal, sem ganho de garantia, não paga o custo de manutenção que as ADRs 0001/0002 já assumem (re-revisão a cada upgrade relevante do Twenty).

**Consequência:** o checklist nativo de tarefas — marcar uma Task como concluída direto pela caixa de seleção em `TaskRow.tsx`, fora do widget "Status agora" — continua sem o mini-formulário: ele só marca a Task como `DONE` (via `useCompleteTask`) e não preenche o campo correspondente nem cria a próxima tarefa da cadeia. Isso é uma limitação conhecida e aceita, não um bug: o campo em si permanece protegido pelo gate de campo da ADR-0002 (não é possível preenchê-lo fora de ordem por nenhum caminho), então o pior caso é uma tarefa marcada como feita sem o trabalho de preenchimento correspondente ter sido feito por "Concluir" — o vendedor ainda precisa editar o campo manualmente nesse caso. Fica como possível fase 2 (patch de core no checkbox nativo, ou um aviso quando a Task é concluída sem o campo correspondente preenchido) se o usuário pedir no futuro.
